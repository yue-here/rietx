# 7g. The project-file readers: what an imported model does not carry

Load it when you read another program's *project* file — a TOPAS `.inp`, a FullProf `.pcr`, a GSAS `.EXP` or a GSAS-II `.gpx` — or its *instrument-parameter* file — a GSAS `.prm` — and a `Diagnostic` came back from the import.

*A reference file of the `rietx` skill. The body it belongs to is [`SKILL.md`](../SKILL.md); section numbers are the ones the body cites.*

These are the codes of `rietx.io.projects` — one module per foreign format,
governed by WP-1118 — together with `rx.read_gsas_prm`'s, which is not a
project reader but emits on the same channel for the same reason. They are a different channel from every other family in
§7, and the difference is the reason they have their own file: **none of them
ever appears on `result.diagnostics`.** A project reader emits them at *import*,
into a list you pass in (`read_topas_inp(..., diagnostics=[])`,
`rietx.io.projects.fullprof.to_structure(..., diagnostics=[])`,
`rx.read_gsas_prm(..., diagnostics=[])`), and if you do
not pass one the finding is still on the model — `model.coverage.reported`,
`model.skipped_blocks`, `species_raw` — but nothing is raised. So the question
these answer is not "is my fit wrong" but **"is the model I just imported the
model that file describes"**, which has to be asked before a fit exists.

Each row states, as the others do, what you must *not* assume once it fires.
Two conventions run across the family. A reader **repairs and reports** where
the repair is a stated, recoverable loss and **refuses** where carrying on
would mean choosing between two readings of the file — so an `_NORMALISED` or
`_DROPPED` code is a repair you can undo, and a `_REFUSED` one is a build that
did not happen. And every construct a format can write is classified in
`rietx.io.projects.coverage`, one row per feature, so support for a construct
arrives by moving its row rather than by growing a reader.

| code | what you must not assume, and what to do |
|---|---|
| `TOPAS_SPECIES_NORMALISED` | (info — from the TOPAS `.inp` reader: pass `read_topas_inp(..., diagnostics=[])` to collect it; it is not on `result.diagnostics`) Assume the model's species are the file's literal tokens. The reader rewrote a sign-first ionic charge (`La+3`, `Cu+1`) onto IUCr digit-first order (`La3+`, `Cu1+`); each message names its substitution and `where` lists the atoms it touched. The `.inp` sibling of `CIF_SPECIES_NORMALISED` |
| `TOPAS_ORIGIN_TRANSLATED` | (info — from the TOPAS `.inp` reader, same channel) Assume the space group is the file's literal symbol. TOPAS writes an origin/axis choice as a letter suffix (`Pn-3mZ`, `R-3cH`) and the reader translated it to the Hermann-Mauguin extension gemmi resolves (`Pn-3m:2`, `R-3c:H`). Not cosmetic: dropping the suffix silently selects the *other* origin — a bare `Pn-3m` is choice 1, so a Cu2O written on choice 2 would be built on the wrong origin's symmetry with nothing raised |
| `TOPAS_BLOCK_SKIPPED` | (warning — from the TOPAS `.inp` reader, same channel) A `str` block stated a cell or sites but no `phase_name`/`space_group`, so the reader could not name it as a phase; it is recorded on `model.skipped_blocks` (never dropped in silence) and this reports what it lacked and what it carried. Building a `Structure` from a model with such a block will **refuse** where other phases build, because dropping a cell-bearing block would leave the weight fractions no longer summing — read `model.phases`/`model.skipped_blocks` to see what the file states |
| `TOPAS_CELL_COUPLING_DROPPED` | (warning — from the TOPAS `.inp` reader, same channel) Two cell keys the file ties together arrived as two independent numbers, because resolving either idiom copies the **value** and not the constraint. The format writes the tie two ways and both are reported: `b = Get(a);`, one edge naming another, and `a = edge; b = edge;`, two edges naming one declared parameter. Reported only where the phase's own space group does **not** already tie the pair — under `P 4/m m m` rietx ties `b ← a` itself and the model says what the file said, so this stays silent (all four coupled files in the corroborating archive are tetragonal or cubic and raise none of these). Where it fires the two edges may refine apart, which is neither what the file meant nor what rietx would have done unaided: tie them in the refinement plan before fitting, or read `model.phases` for the file's own text. The message names which idiom the file used and `where` names the coupled key |
| `TOPAS_FEATURES_NOT_IMPORTED` | (warning — from the TOPAS `.inp` reader, same channel) **The import is partial, and this says how far it goes.** A `.inp` states far more than a structure — peak shapes and convolutions, texture, restraints and penalties, per-reflection controls, scattering-factor overrides — and none of it reaches the built `Structure`. The numbers that do reach it are unaffected; what is missing is the model around them, so a cell or a coordinate is still the file's and an Rwp computed against rietx's own profile is not comparable with the file's. One diagnostic per import, naming each feature and the keywords the file actually wrote. `model.coverage.reported` carries the same list whether or not a `diagnostics=` list was passed, and `model.coverage.partial` is the yes/no |
| `TOPAS_FEATURE_REFUSED` | (warning — from the TOPAS `.inp` reader, same channel) The file states a construct whose *absence* would misrepresent the refinement rather than simplify it — a rigid body (the `site` lines report coordinates the body generated), merged or scaled occupancies (a composition the file does not state once the coupling is gone), a stacking-fault model (the phase does not diffract from the cell it states), or a magnetic structure. `read_topas_inp` **reads** such a file and records it, because the model is still an honest account of the text; `to_structure` is what refuses, naming the construct and what building without it would claim. Read `model.phases` for what the file states and `model.coverage` for every construct the import does not carry. Which construct takes which stance is declared in `rietx.io.projects.coverage`, one row per feature, and support for one arrives by moving its row |
| `GSAS_EXP_HISTOGRAM_NOT_READ` | (warning — from the GSAS `.EXP` reader: pass `read_gsas_exp(..., diagnostics=[])` to collect it, or `read_project_model(..., diagnostics=[])`; it is not on `result.diagnostics`) Assume every histogram in the file reached the model. One did not: it is single-crystal data, or it is time-of-flight or energy-dispersive rather than constant-wavelength, whose profile functions number their coefficients differently. The histogram is still on `model.histograms` with its wavelengths and ranges; what is missing is its **named** profile coefficients, because naming them under a constant-wavelength function's order would mis-assign every width. `model.unsupported` carries the same lines whether or not a `diagnostics=` list was passed |
| `GSAS_EXP_BACKGROUND_NOT_CARRIED` | (info — from the GSAS `.EXP` reader, same channel) Assume the background crossed over. It did not, and it mostly cannot: GSAS's seven background functions include a reciprocal-Q expansion for air scatter and a linear interpolation between fixed points, neither of which is a rietx background. The function number and its coefficients are on `model.histograms[…].background`, so you can see what shape the run fitted; choose your own background and refine it rather than converting the numbers. This is why an Rwp you compute is not comparable with the file's until you have matched the background too |
| `GSAS_EXP_PHASE_MAGNETIC` | (warning — from the GSAS `.EXP` reader, same channel) Assume the phase is nuclear. GSAS phase types 2 and 3 are magnetic, and rietx has no magnetic scattering model, so `to_structure` **refuses** it rather than handing back the nuclear half — which would look complete. The cell and sites are readable on `model.phases`. The same stance the `.inp` and `.pcr` readers take, and it lifts for all three together when the magnetic model lands |
| `GSAS_EXP_SPECIES_NORMALISED` | (info — from the GSAS `.EXP` reader, reported at **build**: pass `diagnostics=` to `to_structure`) Assume the built structure's species are the file's literal tokens. GSAS writes them in upper case (`CA`, `NA`) and the reader title-cases them onto IUCr spelling (`Ca`, `Na`) for the `Structure`, which carries only the one form. `read_gsas_exp` keeps the file's own spelling on `model.phases[…].atoms[…].species`, so the model stays checkable against the file. The `.EXP` sibling of `CIF_SPECIES_NORMALISED` and `FULLPROF_SPECIES_NORMALISED` |
| `GSAS_EXP_COORDINATES_SYMMETRY_FIXED` | (info — from the GSAS `.EXP` reader, reported at build) Assume a site carrying GSAS's `X` refine flag has free coordinates. GSAS's flag means "refine **as permitted by symmetry**", and these sites sit on fully fixed special positions, so nothing of them was free in GSAS either. Carrying the flag onto `x`/`y`/`z` directly would make the whole import raise, because rietx refines coordinates as site-symmetry DOFs and a zero-DOF site refuses a vary request. Nothing is lost here and the parameter count is right; the row exists so that "this site is held" reads as the file's statement rather than as the reader's omission. `where` names the sites |
| `GSAS_EXP_SCALE_NOT_COMPARABLE` | (info — from the GSAS `.EXP` reader, reported at build) Assume the phase scale came from the file. It did not: it is seeded at 1e-3 and left to refine. GSAS's histogram scale folds its own profile normalisation and the phase fraction into one number, so it is not a rietx scale and converting it would be inventing a correspondence. The file's own numbers are on `model.histograms[…].scale` and `model.hap[…].phase_fraction`. Refine the scale rather than trusting a converted value — and for the same reason, phase fractions from the two codes are comparable only after both have refined |
| `GSAS2_GPX_ITEM_NOT_READ` | (warning — from the GSAS-II `.gpx` reader: pass `read_gsas2_gpx(..., diagnostics=[])` to collect it, or `read_project_model(..., diagnostics=[])`; it is not on `result.diagnostics`) Assume everything in the project reached the model. A `.gpx` is a whole GSAS-II session and this reader takes the powder half of it: an image, a single-crystal histogram, a sequential-fit result and a restraint set are each named here and carried nowhere. A **time-of-flight** histogram is the case to watch — it is on `model.histograms` with its numbers, but its coefficients are a different profile function from the one this build fits, so `Gsas2Histogram.constant_wavelength` is what decides whether the terms mean what their names suggest. `model.unsupported` carries the same lines whether or not you passed a list |
| `GSAS2_GPX_BACKGROUND_NOT_CARRIED` | (info — from the GSAS-II `.gpx` reader, same channel) Assume the background crossed over. GSAS-II's own function name and its coefficients are on `model.histograms[…].background`, including the Debye terms and fitted background peaks it counts separately, and none of it is converted: choose your own background and refine it. This is why an Rwp you compute is not comparable with the file's until you have matched the background too — the `.EXP` sibling of this row says the same thing about the older format |
| `GSAS2_GPX_PHASE_MAGNETIC` | (warning — from the GSAS-II `.gpx` reader, same channel) Assume the phase is purely nuclear. It fires in **two** shapes and they differ in what you can do next. A phase GSAS-II types `magnetic` is refused outright by `to_structure`, because the nuclear half would look complete — the same stance the `.inp`, `.pcr` and `.EXP` readers take. A phase typed `nuclear` that carries `Gsas2Phase.magnetic_partner` **does** build, correctly, and the warning is about comparison rather than about the structure: the file's Rwp includes magnetic scattering this build cannot compute, so your fit's figures and the file's are not the same measurement |
| `GSAS2_GPX_CONSTRAINT_NOT_CARRIED` | (warning — from the GSAS-II `.gpx` reader, same channel) Assume the constraints came with the model. They did not: `to_structure` applies none of them, because a tie between parameters the build has not made yet is not a tie. They are on `model.constraints`, each printing as the relation it states, and `Gsas2Constraint.is_equivalence` marks the ones `Refinement.tie_equal` restores in one call each — the count in the message is how many. A hold (`kind == 'h'`) is a `set_vary(path, False)`; a constraint equation and a new variable have no one-call equivalent, so read them before assuming your free set matches the file's |
| `GSAS2_GPX_SPECIES_NORMALISED` | (info — from the GSAS-II `.gpx` reader, reported at **build**: pass `diagnostics=` to `to_structure`) Assume the built structure's species are the file's literal tokens. GSAS-II writes an ionic charge sign first (`Mn+3`, `O-2`) and the reader rewrites it to IUCr spelling (`Mn3+`, `O2-`) for the `Structure`, which carries only the one form. `read_gsas2_gpx` keeps the file's own spelling on `model.phases[…].atoms[…].species`, so the model stays checkable against the file. The `.gpx` sibling of `CIF_SPECIES_NORMALISED` and `FULLPROF_SPECIES_NORMALISED` |
| `GSAS2_GPX_COORDINATES_SYMMETRY_FIXED` | (info — from the GSAS-II `.gpx` reader, reported at build) Assume a site carrying GSAS-II's `X` refine flag has free coordinates. That flag means "refine **as permitted by symmetry**", and these sites sit on fully fixed special positions, so nothing of them was free in GSAS-II either. Carrying the flag onto `x`/`y`/`z` directly would make the whole import raise, because rietx refines coordinates as site-symmetry DOFs and a zero-DOF site refuses a vary request. Nothing is lost and the parameter count is right; the row exists so that "this site is held" reads as the file's statement rather than as the reader's omission |
| `GSAS2_GPX_SCALE_NOT_COMPARABLE` | (info — from the GSAS-II `.gpx` reader, reported at build) Assume the phase scale came from the file. It did not: it is seeded at 1e-3 and left to refine. GSAS-II keeps a histogram scale *and* a per-phase scale, each folding its own normalisation into one number, so neither is a rietx scale and converting one would be inventing a correspondence. The file's numbers are on `model.histograms[…].sample['Scale']` and `model.hap[…].scale`. Refine the scale rather than trusting a converted value — and for the same reason, phase fractions from the two codes are comparable only after both have refined |
| `FULLPROF_SPECIES_NORMALISED` | (info — from the FullProf project reader: pass `rietx.io.projects.fullprof.to_structure(..., diagnostics=[])` to collect it; it is not on `result.diagnostics`) Assume the built structure's species are the `.pcr`'s literal scattering tokens. FullProf writes that token in whatever case the author typed (`CR`) and can write a sign-first charge (`CA+2`); the reader case-folds and reorders it onto IUCr spelling (`Cr`, `Ca2+`) for the `Structure`, which carries only the one form. `read_fullprof_pcr` keeps the raw token beside it on `species_raw`, so the model is checkable against the file even without this — the code fires only at the build, where the raw form is dropped. Each message names its substitution and `where` lists the atoms it touched; a magnetic form-factor label (`MCR3`) is left verbatim |
| `FULLPROF_ORIGIN_CHOICE` | (info — from the FullProf project reader, same channel) Assume the built phase's space group is the `.pcr`'s literal symbol. FullProf writes **no** origin-choice or axes suffix at all, so the setting was chosen by the reader: origin choice 2 where the bare symbol resolves to 1 (`F D -3 M` → `F d -3 m:2`, the spinel case), and rhombohedral axes where the cell says so (a bare `R -3 c` over an a = b = c, α = β = γ cell → `R -3 c:R`). Not cosmetic: the two R settings differ by a factor of three in general multiplicity, and an origin choice moves every special position. The choice is licensed by the occupancy-ratio check, which a wrong setting fails — except where `FULLPROF_OCCUPANCY_UNCHECKED` also fired, and then it is unlicensed |
| `FULLPROF_OCCUPANCY_UNCHECKED` | (warning — from the FullProf project reader, same channel) Assume the origin/axes choice above was verified. The check that verifies it compares each site's `Occ × M_general / M_site` and requires them to agree, but the phase has a **single site**, so it compared one number with itself and passed for every setting. That is not repairable by a better test — FullProf's `Occ` carries one arbitrary per-phase factor, so one site is one equation in two unknowns — so confirm the setting against the published structure yourself, or add a site. `where` names the site whose occupancy could not discriminate |
| `FULLPROF_TIE_DROPPED` | (warning — from the FullProf project reader, same channel) Assume the built `Structure` has the same free parameters as the refinement the `.pcr` records. It has **more**: a `.pcr` writes a tie by giving two values one parameter number, and this one is not reproduced by rietx. Whether that **reports** or **refuses** turns on one question — can you put the tie back in a single unambiguous call? A **cell** tie the space group does not hold equal (`a = b` under an orthorhombic or triclinic symbol, or a scaled `b = 2a` symmetry never expresses) and a **cross-site** tie in `Biso`/`Occ` **or in one coordinate column where every site involved has exactly one DOF** all report, because the restoring call is exact; this matches `TOPAS_CELL_COUPLING_DROPPED` one reader over, so the two readers say the same thing about the same defect. A tie whose restoring call would be a *choice* **refuses** instead — a group spanning different columns on different atoms, or a coordinate group touching a site whose DOF count is not 1, since `dof.k` on two different sites is not the same direction. `to_structure(..., drop_parameter_ties=True)` is how you declare you accept the looser model in that case, and the message then says so. Either way, re-declare the constraint on the refinement — and **mind which spelling the call takes**: `Refinement.tie_equal(['phases.i.atoms.j.biso', ...])` on the column paths for a `Biso`/`Occ` group, but on the **DOF paths** (`Refinement.tie_equal(['phases.i.atoms.j.dof.k', ...])`) for a coordinate group, because a coordinate column already follows its own `dof` by site symmetry and `tie_equal` refuses to outrank that — `phases.0.atoms.1.x` raises `already follows 'phases.0.atoms.1.dof.0' (symmetry)` even though the group description names `.x`. `Refinement.tie(path, source, scale=multiplier)` for a signed one. Then the parameter count is restored |
| `GSAS_PRM_FIELD_DROPPED` | (info — from `rx.read_gsas_prm`, same channel) Assume the returned `Instrument` carries everything the `.prm` states. It carries what `ProfileTCHZ` and `Geometry` have room for, and one of these fires per record that held something else **at its identity value**: `ICONS` (a zero `LAM2` or `ZERO`, the polarization type `IPOLA`, the refine flags and `IDAMP`, and `KRATIO` where the file states no second line to weight), `PRCF` (`GP` and every coefficient past position 8, all 0), and `IRAD`/`ITYP`, ignored by design because the wavelength is read from `ICONS` rather than looked up and an angular range belongs to the pattern. A **non-zero** value in any of those raises instead of reporting: the rule is refuse at drift, report at the model's identity, so an `info` here means the file agreed with the model rather than that something was lost. `where` names the record. **A file stating a doublet comes back with two emission lines**, the second weighted by `KRATIO`, and the `ICONS` row says so — so do not add a Kα2 line yourself after reading one (Measured: WP-1118) |
| `GSAS_PRM_GEOMETRY_ASSUMED` | (warning — from `rx.read_gsas_prm`, same channel) **Do not assume the geometry was read: a `.prm` does not state one.** `HTYPE PXCR` spans Bragg-Brentano and Debye-Scherrer and the format gives nothing to tell them apart, so the reader returns `Instrument.debye_scherrer` — a capillary, `packing_fraction=0.6` — because that is what the corpus behind the reader is, and fires this every time rather than inferring. It matters more than a dropped zero: `Geometry.kind` selects the position correction and its suggested action, and the two geometries' absorption corrections have different *off* states (`mu_r = 0` against `mu_t = ∞`), so a flat-plate calibration read this way arrives with the wrong half of that machinery armed. If the calibration is from a flat-plate diffractometer, set the geometry yourself before fitting — and **carry `geometry.axial_sl` and `geometry.axial_hl` over to the replacement**, because `PRCF` positions 7-8 (`S/L`, `H/L`) were read from the file and land on the geometry, so a `Geometry` built from scratch has no axial divergence at all |
