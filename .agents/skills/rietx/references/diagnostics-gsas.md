# 7h. The GSAS and GSAS-II readers and writers: what their files do not carry

Load it when you read a GSAS `.EXP` or a GSAS-II `.gpx` project file, a GSAS `.prm` or `.iparm` or a GSAS-II `.instprm` instrument-parameter file (a constant-wavelength or a time-of-flight one), or when you write one of those back or export a phase CIF for GSAS-II, and a `Diagnostic` came with it.

*A reference file of the `rietx` skill. The body it belongs to is [`SKILL.md`](../SKILL.md); section numbers are the ones the body cites.*

These are the codes of `rietx.io.projects.gsas` and `rietx.io.projects.gsas2`,
together with the instrument-file and phase-CIF pairs `rx.read_gsas_prm` /
`rx.write_gsas_prm`, `rx.read_gsas2_instprm` / `rx.write_gsas2_instprm` and
`rx.write_gsas2_phase_cif`. They are §7g's channel and not the engine's: a
reader or a writer emits them into a list you pass in
(`rx.read_gsas_exp(..., diagnostics=[])`, `rx.read_gsas2_gpx(...,
diagnostics=[])`, `rx.read_gsas_prm(..., diagnostics=[])`), and none of them
ever reaches `result.diagnostics`. §7g,
[`references/diagnostics-projects.md`](diagnostics-projects.md), states that
rule in full and holds the TOPAS and FullProf rows.

The two programs share a file because their row sets are parallel and a
migration reads them against each other. Five of the `.EXP` suffixes are also
`.gpx` suffixes, and two of the `.prm` ones are also `.instprm` ones, so the
row you want sits beside the row you are comparing it with. The **writer** rows
are here too. A `.EXP`, a `.prm`, an `.instprm` and a GSAS-II phase CIF are all
written back, this build writing no `.gpx`, and what a writer could not carry is
as much a difference from the other program's answer as what a reader could not
read.

Each row states, as the others do, what you must *not* assume once it fires.
Two conventions run across the family. A reader **repairs and reports** where
the repair is a stated, recoverable loss and **refuses** where carrying on
would mean choosing between two readings of the file — so an `_NORMALISED` or
`_DROPPED` code is a repair you can undo, and a `_REFUSED` one is a build that
did not happen. And every construct a format can write is classified in
`rietx.io.projects.coverage`, one row per feature, so support for a construct
arrives by moving its row rather than by growing a reader.

| code | what you must not assume, and what to do |
|---|---|
| `GSAS_EXP_HISTOGRAM_NOT_READ` | (warning — from the GSAS `.EXP` reader: pass `read_gsas_exp(..., diagnostics=[])` to collect it, or `read_project_model(..., diagnostics=[])`; it is not on `result.diagnostics`) Assume every histogram reached the model. The histogram is still on `model.histograms` with its wavelengths and ranges, without named profile coefficients. `model.unsupported` carries the same lines whether or not a `diagnostics=` list was passed |
| `GSAS_EXP_BACKGROUND_NOT_CARRIED` | (info — from the GSAS `.EXP` reader, same channel) Assume the background crossed over. It did not. The function number and coefficients are on `model.histograms[…].background`: choose your own background and refine it rather than converting them |
| `GSAS_EXP_PHASE_MAGNETIC` | (warning — from the GSAS `.EXP` reader, same channel) Assume the phase is nuclear. `to_structure` **refuses** it. The cell and sites are readable on `model.phases`. A magCIF of the same structure is the route that reads: `Structure.from_cif` (§7j, `references/magnetic.md`) |
| `GSAS_EXP_SPECIES_NORMALISED` | (info — from the GSAS `.EXP` reader, reported at **build**: pass `diagnostics=` to `to_structure`) `read_gsas_exp` keeps the file's own spelling on `model.phases[…].atoms[…].species`, so check the model against that, not against the `Structure`. The `.EXP` sibling of `CIF_SPECIES_NORMALISED` and `FULLPROF_SPECIES_NORMALISED` |
| `GSAS_EXP_COORDINATES_SYMMETRY_FIXED` | (info — from the GSAS `.EXP` reader, reported at build) Nothing to act on. Do not carry the flag onto `x`/`y`/`z` by hand: a zero-DOF site refuses a vary request. `where` names the sites |
| `GSAS_EXP_SCALE_NOT_COMPARABLE` | (info — from the GSAS `.EXP` reader, reported at build) Do not read the scale as the file's. The file's own numbers are on `model.histograms[…].scale` and `model.hap[…].phase_fraction`. Refine the scale, and compare phase fractions between the two codes only after both have refined |
| `GSAS_EXP_VALUE_NARROWED` | (info — from the GSAS `.EXP` **writer**: pass `write_gsas_exp(..., diagnostics=[])` to collect it) Fires once per file, naming how many values and the worst; `where` lists every one. A displacement is always among them: about seven significant figures survive, 1e-7 of the value against an esd of ~1e-2. Nothing to act on unless you are comparing bit patterns |
| `GSAS_EXP_REFINE_FLAG_MERGED` | (warning — from the GSAS `.EXP` writer, same channel) Do not assume the file's refine flags are your `Structure`'s. The row names the group. A round trip through this writer does not return what it was given, so hold the whole group, or free it, if the distinction matters |
| `GSAS_EXP_SPECIES_WRITTEN_NEUTRAL` | (warning — from the GSAS `.EXP` writer, same channel) `value` is the fractional error on \|f\| at s = 0 and `where` lists every site. `SPECIES_FALLBACK_NEUTRAL` is the same fact at fit time. No writer refuses a species for its charge (WP-1527). A digitless ion the table carries is not named: `Cu+` is written `CU+1` |
| `GSAS2_GPX_ITEM_NOT_READ` | (warning — from the GSAS-II `.gpx` reader: pass `read_gsas2_gpx(..., diagnostics=[])` to collect it, or `read_project_model(..., diagnostics=[])`; it is not on `result.diagnostics`) Assume everything in the project reached the model. For a **time-of-flight** histogram, `Gsas2Histogram.constant_wavelength` decides whether its terms mean what their names suggest. `model.unsupported` carries the same lines whether or not you passed a list |
| `GSAS2_GPX_BACKGROUND_NOT_CARRIED` | (info — from the GSAS-II `.gpx` reader, same channel) Assume the background crossed over. Its function name and coefficients are on `model.histograms[…].background`, including the Debye terms and fitted background peaks GSAS-II counts separately. Choose your own and refine it. The `.EXP` sibling says the same of the older format |
| `GSAS2_GPX_PHASE_MAGNETIC` | (warning or info — from the GSAS-II `.gpx` reader, same channel) Assume the project is purely nuclear. It fires in **two** shapes. A phase GSAS-II types `magnetic` (warning) is refused by `to_structure`; a magCIF of the structure reads through `Structure.from_cif`. A phase typed `nuclear` that carries GSAS-II's `magPhases` entry (`Gsas2Phase.magnetic_partner`) builds, and the row says whether the entry is one of the project's histogram names and how many magnetic phases the project holds. With none it is **info**: nothing magnetic is modelled, and the file's Rwp is a nuclear figure. (Measured, #606: on the five public projects checked that carry the entry it is a histogram name and there is no magnetic phase.) The entry is kept verbatim and not interpreted, since GSAS-II does not document it |
| `GSAS2_GPX_CONSTRAINT_NOT_CARRIED` | (warning — from the GSAS-II `.gpx` reader, same channel) They are on `model.constraints`, each printing as the relation it states. `Gsas2Constraint.is_equivalence` marks the ones `Refinement.tie_equal` restores in one call each; the message counts them. A hold (`kind == 'h'`) is a `set_vary(path, False)`. Read a constraint equation or a new variable before assuming your free set matches the file's |
| `GSAS2_GPX_SPECIES_NORMALISED` | (info — from the GSAS-II `.gpx` reader, reported at **build**: pass `diagnostics=` to `to_structure`) `read_gsas2_gpx` keeps the file's own spelling on `model.phases[…].atoms[…].species`, so check the model against that. The `.gpx` sibling of `CIF_SPECIES_NORMALISED` and `FULLPROF_SPECIES_NORMALISED` (isotopes: issue #554) |
| `GSAS2_GPX_COORDINATES_SYMMETRY_FIXED` | (info — from the GSAS-II `.gpx` reader, reported at build) Nothing to act on. Do not carry the flag onto `x`/`y`/`z` by hand: a zero-DOF site refuses a vary request |
| `GSAS2_GPX_SCALE_NOT_COMPARABLE` | (info — from the GSAS-II `.gpx` reader, reported at build) Do not read the scale as the file's. The file's numbers are on `model.histograms[…].sample['Scale']` and `model.hap[…].scale`. Refine the scale, and compare phase fractions between the two codes only after both have refined |
| `GSAS2_GPX_TEXTURE_CONVERTED` | (info — from the GSAS-II `.gpx` reader, reported at build) Each coefficient was multiplied by P_l(0), and by √2 on the n ≠ 0 terms of 4/m, −3 and 6/m. Fit under the `bragg_brentano` geometry and the multipliers are GSAS-II's (Measured: 12 Laue settings against GSAS-II 5.8.4's own P, to its single precision). Compare coefficients with GSAS-II only through this conversion; `model.hap[…].texture` holds the file's numbers |
| `GSAS2_GPX_TEXTURE_NOT_CARRIED` | (warning, or info where nothing is lost: a cubic class with no term below the entry's order, so P is 1 at every reflection; same channel) Assume the phase carries the file's texture. It does not. The message names the cause; the terms GSAS-II itself evaluates wrongly are n ≠ 0 in −1 and 2/m, rhombohedral axes and −31m's n = 3. Declare `Phase.texture` yourself and refine it from zero rather than converting those numbers. The file's own are on `model.hap[…].texture` |
| `GSAS2_GPX_SETTING_FROM_OPERATORS` | (info — from the GSAS-II `.gpx` reader: pass `read_gsas2_gpx(..., diagnostics=[])`) Nothing is lost and nothing is owed. The built `Structure` carries a symbol (`'F d d d:2'`) that is not the file's string, which `Gsas2Phase.space_group` still holds beside `.resolved_space_group`. (Measured: in all four tutorial-corpus phases that write a bare two-setting symbol, the operators are origin choice 2 where the symbol resolves to choice 1.) This is why the `.gpx` route does **not** raise `SPACE_GROUP_SETTING_ASSUMED` where the `.EXP` and `.inp` routes do: those state a symbol and no operators, so the reader says so at read |
| `GSAS_FIELD_OVERFLOW` | (warning — from `rx.read_gsas_exp` and `rx.read_gsas_prm`, same channel) Assume a `None` on the model means the file left the field out. It fires only for an **optional** field (an esd, the history `RPOWD` Rwp, `KRATIO`); `where` names the record key. An overflow in a **required** field (a cell edge, a coordinate, a `.prm`'s `LAM1`) refuses the read, and so does one in a profile or background coefficient. Take the value from GSAS's own listing |
| `GSAS_PRM_FIELD_DROPPED` | (info — from `rx.read_gsas_prm`, same channel) One fires per record that held something else **at its identity value**: `ICONS` (a zero `LAM2` or `ZERO`, `IPOLA`, the refine flags and `IDAMP`, `KRATIO` with no second line), `PRCF` (`GP` and every coefficient past position 8, all 0), and `IRAD`/`ITYP`, ignored by design. A **non-zero** value in any of those raises instead: refuse at drift, report at the model's identity. `where` names the record. **A file stating a doublet comes back with two emission lines**, the second weighted by `KRATIO`, so do not add a Kα2 line yourself after reading one (Measured: WP-1118). **An `HTYPE PNCR` file's `POLA` is the one non-zero value dropped rather than refused**: a neutron source pins its polarisation term at 1 (Measured: WP-1312, HB-2A's `POLA 0.990`) |
| `GSAS_PRM_GEOMETRY_ASSUMED` | (warning — from `rx.read_gsas_prm`, same channel) **Do not assume the geometry was read: a `.prm` does not state one.** The reader returns `Instrument.debye_scherrer` (a capillary, `packing_fraction=0.6`) every time, since `HTYPE PXCR` spans both geometries. `Geometry.kind` selects the position correction and its suggested action, and the two absorption corrections have opposite *off* states (`mu_r = 0` against `mu_t = ∞`). For a flat-plate calibration set the geometry yourself, and **carry `geometry.axial_sl` and `geometry.axial_hl` over to the replacement**: `PRCF` positions 7-8 landed on the geometry, and a `Geometry` built from scratch has no axial divergence. On an `HTYPE PNCR` file the instrument is `Instrument.constant_wavelength_neutron`, also Debye-Scherrer (Measured: WP-1312) |
| `GSAS_PRM_PROFILE_SET_DEFAULTED` | (warning — from `rx.read_gsas_prm`, same channel) The message lists each set's type. Only type 3 is read, so name another type-3 set with `profile_set=N` if set 1 is not the calibration you meant. A type-1 set 1 beside a type-3 set is refused, and the refusal names the set to pass (Measured: WP-1543, GSAS-II's `BT1_Cu311.inst`) |
| `GSAS_PRM_FIELD_NOT_WRITTEN` | (warning — from `rx.write_gsas_prm`: pass `diagnostics=[]`) Assume an exported `.prm` is your whole instrument. Reading it back gives `debye_scherrer`: the writer's side of `GSAS_PRM_GEOMETRY_ASSUMED`. `S/L` and `H/L` are the two geometry numbers that do cross. The row also names a true-Voigt profile (GSAS's type 3 has no Voigt option, so the shape model becomes the target's), any `extra_components`, and the refine flags |
| `GSAS_PRM_VALUE_NARROWED` | (info — from `rx.write_gsas_prm`: pass `diagnostics=[]`) The ordinary case on a converged calibration, not a warning sign: the centidegree conversion adds the product's own float noise, so a `u` of 0.0043710000000001 becomes a `GU` of 43.710000000000996 and then the characters the field allows. The `.prm` twin of `GSAS_EXP_VALUE_NARROWED` |
| `GSAS2_INSTPRM_CONVENTION_ASSUMED` | (info — from `rx.read_gsas2_instprm`: pass `diagnostics=[]`) The even split is the only one a single number admits. `rx.read_recipe` makes the same split for the same field. If you know the slit and detector heights differ, set the pair yourself |
| `GSAS2_INSTPRM_GEOMETRY_ASSUMED` | (warning — same reader) **Do not assume the geometry was read: this file stated no `Diff-type`.** The fallback is GSAS-II's own, and the two geometries' absorption corrections have opposite off states (µR = 0 against µt = ∞). Set `geometry.kind` yourself if you know the diffractometer, and carry `axial_sl`/`axial_hl` over first, since `SH/L` *was* read from the file and a fresh `Geometry` starts both at 0 |
| `GSAS2_INSTPRM_VALUE_DEFAULTED` | (warning — same reader) Assume every coefficient came from the file. The named items came back at this package's defaults, so check the values the file does state before trusting the instrument |
| `GSAS2_INSTPRM_FIELD_NOT_READ` | (info — same reader) Assume the whole file crossed. On a `PNC` (neutron) bank `Polariz.` is inert in **both** packages: GSAS-II applies the polarization factor only to an `XC` or `XB` type, and `NeutronSource` pins K = 1 |
| `GSAS2_INSTPRM_VALUE_MERGED` | (warning — from `rx.write_gsas2_instprm`: pass `diagnostics=[]`) Fires only where `axial_sl` and `axial_hl` differ, the one case the merge loses something. Reading the file back gives half the sum twice |
| `GSAS2_INSTPRM_VALUE_FLOORED` | (warning — same writer) The floor is 0.002. No round trip through this package can show it: the floor is the other reader's, not the file's |
| `GSAS2_INSTPRM_FIELD_NOT_WRITTEN` | (warning — same writer) Assume an exported `.instprm` is your whole instrument. GSAS-II keeps absorption, displacement and transparency in its *sample* parameters, and a calibration ships with nothing refined. A true-Voigt profile is named too: GSAS-II's constant-wavelength function has no Voigt option, so the shape model becomes the target's |
| `GSAS2_CIF_SETTING_IN_OPERATORS` | (info — from `rx.write_gsas2_phase_cif`: pass `diagnostics=[]`) GSAS-II resolves a bare two-origin symbol such as `F d -3 m` to origin choice **2** and answers a colon-suffixed one by setting the phase to `P 1`, while gemmi resolves the bare string to choice **1**. The file states the setting in `_symmetry_space_group_name_H-M` (bare), `_space_group_name_H-M_alt` (resolved) and `_space_group_symop_operation_xyz`, the channel GSAS-II checks its own reading against. Read the operations, never the symbol, if a third program opens the file |
| `GSAS2_CIF_DEUTERIUM_AS_D` | (info — same writer) `2H` is respelled `D`, the one isotope label GSAS-II's import takes. GSAS-II scatters D at b = 6.681 fm against rietx's 6.671 fm (Sears), so that refinement starts 0.15 % away on those sites |
| `GSAS2_CIF_SPECIES_WRITTEN_NEUTRAL` | (warning — same writer) The phase-CIF twin of `GSAS_EXP_SPECIES_WRITTEN_NEUTRAL`. `Cu+` is written `Cu1+`, which GSAS-II stores as `Cu+1`; its importer reads a bare `Cu+` as carbon |
| `GSAS2_CIF_RHOMBOHEDRAL_RESTATED` | (warning — from `write_gsas2_phase_cif`: pass `diagnostics=[]`) The cause is GSAS-II's CIF import, which refuses rhombohedral axes ("a space group setting not compatible with GSAS-II"). The CIF has the hexagonal cell, every parameter held and the scale divided by 9 (a CIF carries no scale). Same crystal; free what you mean to refine |
| `GSAS2_CIF_FIELD_NOT_WRITTEN` | (warning — same writer) Assume a GSAS-II project built from this CIF starts where your refinement did. It starts from that program's defaults for refine flags, phase scale and sample broadening. Any Stephens strain, preferred orientation, extinction or restraints the phase carries are named, because a CIF has no tags for them |

## The time-of-flight instrument-parameter readers

`rietx.io.instrument_tof`'s two readers open a bank's *calibration*, never a
model — no phase, no structure, so `rietx.io.projects.coverage` has nothing to
classify — which is why their codes sit beside the other GSAS and GSAS-II instrument
rows and not with the project families of §7g: they answer the same question ("is what I just imported the
file I meant to import"), about a bank instead of a phase. This build reads
a bank and refines none.

| code | what you must not assume, and what to do |
|---|---|
| `GSAS_IPARM_PROFILE_DECLINED` | (warning for a bank with no `PRCF` set, info for a non-default set; from `rx.read_gsas_tof_iparm`, same channel) **Do not assume the returned bank carries the file's peak shape.** Set 1 is the default whatever its type and the only one read. A bank with no `PRCF` set carries its calibration and an all-zero `ProfileTOF`, which says no profile was read. A default set the package cannot read (wrong `NCOF`, profile type 2/4/5, a non-zero anisotropic term) is **refused** at read rather than declined. Declare `instrument.source.profile_tof` by hand, or read the bank's `.instprm`, whose keys are named and whose profile *is* read |
| `GSAS_IPARM_PROFILE_READ` | (info — from `rx.read_gsas_tof_iparm`, same channel) **Check the coefficients before you refine on them: the record order is an assumption.** The default `PRCF` set (type 1 with 12 coefficients, or type 3 with 21) was read in the order the GSAS manual lists the names; the manual never states that this is the record order. `CTOF` is quoted and not used. Everything read arrives `vary=False`, like the calibration beside it |
| `GSAS_IPARM_FIELD_DROPPED` | (info — from `rx.read_gsas_tof_iparm`, same channel) Assume the returned banks carry everything the file states. They carry `ICONS` (DIFC/DIFA/ZERO), `BNKPAR` (DIST as L₂, TTHETA as the bank's 2θ) and `FPATH1` (L₁). `ITYP`/`ICOFF`/`IECOF` **are** read onto `instrument.source.incident_spectrum`; `IECOR`, the correlation matrix, is not. Fires once per file, `where` listing the records |
| `GSAS_IPARM_LEGACY_LAYOUT` | (info — from `rietx.io.legacy.read_lansce_iparm`, same channel) **Do not assume the file met the GSAS manual's layout; it met the legacy LANSCE one.** Each report names one of three deviations by its last `where` entry. `PRCF1`: a type-1 block of 8 coefficients, read as the first eight of the documented twelve (slots 9-12 zero) and then through the strict reader, so the `GSAS_IPARM_PROFILE_READ` beside it describes that restated block; slots 1, 5, 8 are `alp-0`, `sig-0`, `s1ec` by the manual's order, which GSAS-II leaves unnamed. `ICOFF3`: a non-zero ITYP 1/2 fifth pair, carried as written. `BNKPAR`: one record ran a value across a field boundary and was re-read by tokens; the message quotes the raw text and the value taken, so check the angle. Only `rietx.io.legacy.read_lansce_iparm` emits it, and only when called by name: `rx.read_gsas_tof_iparm` refuses the same file |
| `GSAS2_INSTPRM_FIELD_DROPPED` | (info — from `rx.read_gsas2_instprm` on a `Type: PNT` bank, same channel) Assume every key of the `.instprm` reached the `Instrument`. `beta-q` and `sig-q` are dropped **only at 0**; a non-zero one raises, the refuse-at-drift rule of the other readers. `fltPath` is the *total* flight path L₁ + L₂ and the file does not say where the sample sits, so it is reported rather than assigned to either leg. `Bank` is reported and not used: the GSAS-II Magnetic-V tutorial ships two different banks both declaring `Bank:1.0`, so the key is not an identifier |
