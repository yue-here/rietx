# 7j. The magnetic family: a satellite, a stated moment and the child group it implies

Load it when a magnetic `Diagnostic` fired — from `analyse_moments` on a fit's `FitReport.magnetic` rows, from `solve_magnetic`'s `MagneticSolution`, from `magnetic_supercell`'s returned statement, or from a magCIF/TOPAS/FullProf import — when you were handed a magnetic structure to read, or before you read `FitReport.satellites`.

*A reference file of the `rietx` skill. The body it belongs to is [`SKILL.md`](../SKILL.md); section numbers are the ones the body cites.*

The magnetic diagnostic family lives in this one file rather than in §7's tables (`references/diagnostics.md`; maintainer ruling, issue #286): one order-parameter question, one file. **The channel varies by table**, and each row says which:

* **Moment codes** are about a refined moment (WP-1327) and ride on the report's `MomentEvidence` rows (`analyse_moments`, `FitReport.magnetic`); the **magnetic-width codes** (WP-1343) ride on `result.diagnostics`.
* **Candidate codes** are not on `result.diagnostics` at all: they are on the `SupercellStatement` `magnetic_supercell` returns, because the question — does a Hermann-Mauguin symbol name the child group this cell carries — is settled before a fit exists, the same way a project reader's own codes are.
* The **satellite arm** (WP-1326, `FitReport.satellites`) emits no code at all; its readings are in the next section.
* **Series codes** (WP-1329) ride on a `SeriesResult`, from a series of patterns with a refined moment: the held-moment and onset-bracket codes.
* The **determination verb** (WP-1418, `solve_magnetic`) answers on the `MagneticSolution` it returns, readings and codes in one table.
* **Interchange codes** are about a magnetic structure read from a file (WP-1328) and fire at *import* — pass `diagnostics=[]` to the reader to collect them; they never reach `result.diagnostics`.

## The satellite arm

| reading | what you must not assume, and what to do |
|---|---|
| `SatelliteCandidate.matched` at the top of `SatelliteEvidence.candidates` | Read the top row as the propagation vector. The count has no chance baseline: on the Cr₂WO₆ tutorial set the best zone-boundary k indexes 2 of 6 leftover peaks at 4 K and 2 of 5 at 150 K, where there is no order. Compare `matched` with `n_satellites` (a k with a line everywhere matches by being everywhere) and with the runner-up (the note quotes all three, and calls a tie), then declare the k (`Phase.propagation_vector`) and run a Le Bail or Pawley stage: whether the extraction puts intensity on the satellites is the measurement |
| `SatelliteEvidence.excess_on_absent_lattice_lines` > 0 | Read it as a k = 0 magnetic structure. The points are forbidden only under the group you assumed: a lower nuclear group, λ/2 contamination and an impurity line also put intensity there, and on X-rays magnetism is not a cause at all. Rule those out first; on neutrons, then test a moment model under a k = 0 magnetic space group (§7j above), not a propagation vector, which refuses k = 0 |
| `SatelliteEvidence.excess_on_nuclear_lines` > 0 | Call it magnetic or nuclear from this pattern. A k = 0 structure and a nuclear misfit look alike here; a pattern of the same specimen above its ordering temperature separates them |
| `SatelliteEvidence.radiation == "xray"` | Call intensity at G ± k magnetic. On X-rays it is a superstructure reflection |

## The determination verb

`rx.solve_magnetic` (signatures: [`api-magnetic.md`](api-magnetic.md)) answers with a `MagneticSolution`, provisional by declaration. Its codes ride on `MagneticSolution.diagnostics`, never on `result.diagnostics`; `MAGNETIC_ION_ASSUMED` and `LANDE_G_ASSUMED` (interchange rows below) arrive there too when the solve had to resolve a site's ion.

| reading or code | what you must not assume, and what to do |
|---|---|
| `MagneticSolution.verdict == "abstained"` | Pick a class from `trials` yourself, or widen `tie_width` until one wins. The leading classes lie inside `tie_width` ΔBIC; `tied` names them, fewest moment parameters first (the highest-symmetry convention's order), and `reason` gives each one's parameter count and R_mag, neither of which ranks them. Report the tie with every tied class, and separate them with data (another temperature, a single crystal) rather than with a threshold. The same verdict with every class **refused** is a statement about what could be modelled, not about the specimen, and `reason` says so |
| `MagneticSolution.verdict == "nothing to solve"` | Read it as a search that failed. No refined class both carries a supported moment (WP-1327's null test) and improves on the nuclear model (ΔBIC > 0), which is the answer for a pattern above its ordering temperature. A class can clear the null test and still be here, so read `reason` for which half failed. On the Cr₂WO₆ tutorial set at 150 K the converged class fails both, its moments at 1e-4 μ_B and ΔBIC −37 (Measured: WP-2002, at N/f²). A trial whose fit still stops on its iteration budget after `SOLVE_MAX_CONTINUATIONS` continuations has `fit_status` `"max_iter"` and is listed, not ranked (Measured: WP-1418, WP-1954) |
| `MagneticTrial.members` longer than one | Report the representative as the structure. The members are models this pattern, to `MagneticSolution.d_min`, cannot separate; quote the class and name them all |
| `MagneticSolution.margin` | Diff `trials[0].delta_bic` against `trials[1]` by hand. `trials` lists the eligible classes and then the rest, so the second row can be an unsupported class with a higher raw ΔBIC; `margin` is over the best *other eligible* class and is `None` on an abstention |
| `MomentRow.paired_with` non-empty | Quote `MomentRow.magnitude` or judge the row by `MomentRow.supported`. The two moduli ride a flat direction and each fails the null test alone; the powder measures `paired_magnitude`, and the gate reads `MomentRow.pair_supported` for it |
| `SOLVE_B_TIED_PER_PARENT_SITE` | (info; only with `solve_magnetic(tie_to_parent=True)`) Coordinates were held as always; the tie covers the cell and Biso only. |
| `K_VECTOR_UNSEPARATED` | (info) Treat the winning propagation vector as settled. `k_trials` holds one row per k actually refined. The code tests the gap of the top two entries against `k_tie_width` ΔBIC (default 10.0) and nothing else, whatever the message says about the satellite step. |
| `MAGNETIC_SUBGROUP_PREFERRED` | (**warning**) Trust the ranked list's top row without reading `MagneticSolution.subgroup_note`. `value` is the margin and the message names both groups. The code reports; it does not change `MagneticSolution.best`. Only a k = 0 winner is audited, and a k ≠ 0 winner's note says the audit was not attempted |

## Moment codes

| code | what you must not assume, and what to do |
|---|---|
| `MOMENT_PAIR_DEGENERATE` | (info — from `report.magnetic.moment_pair_diagnostics` over `analyse_moments`' rows) Read either site's own `MomentEvidence.magnitude` for a paired row. The pair is `MomentEvidence.paired_magnitude` and `.paired_magnitude_esd`, `paired_with` naming the other site. On a `solve_magnetic` solution the message opens with `class N` (and `k = (…)` off Γ): the pairs of every class tried are listed there, so read the winner's own `MagneticTrial.moments` for its rows |
| `PLAN_FREES_NO_MOMENT` | (**warning**, from the *plan*, before the first stage runs; `where` is each held site's modulus path) Quote the moment, or the nuclear values fitted beside it: the moment is your start value, with no esd. `mccusker_default` and `mccusker_structural` free none. Use `plan="magnetic_structural"` (moduli, then every moment DOF, then the structural order, the moments free to the end). A moment you `hold` is left out. In a series, `SEQUENTIAL_MOMENT_HOLD` names it as the cause |
| `MOMENT_ANGLE_STATIONARY` | (info — on `result.diagnostics`, from the last stage's `StageResult.moment_angle_tests`) Do not read a `where` angle's missing esd as unmeasured, nor quote it ± an esd. Quote it by its row's `RefinedParameter.interval`, the 95 % profile interval a single fit computes unasked; the message says whether it includes the symmetry direction. A joint fit computes none. The other esds stop depending on where the solver stopped (Measured: two-site Pnma moduli 0.031/0.159 → 0.0015/0.0011 μ_B, WP-1929; the intervals cost 20-32 refits an angle, 2.6-16.7 s on 0.2-1.2 s fits, WP-2002). `value` is Δχ²/(χ²_red·f²), under the round's `cut` |

**A held moment direction is not a code.** It is in `StageResult.held` (`…moment.dof1`/`dof2`) and in `MomentEvidence.unmeasured_directions`. Do not quote a held angle as measured: it has no esd because the powder cannot see it (Shirane, *Acta Cryst.* **12**, 282, 1959). On a site whose flat rotation is a combination of the two angles (a uniaxial powder on axes whose frame pole is not the unique axis, e.g. R-3m:R about [111]), the fit first turns the moment about that axis and then holds the azimuth. `StageResult.moment_flat_axes` names the axis and `.moment_turned` records the turn. The reported `crystalaxis` direction is then one of a cone of equally good ones; quote the angle to the axis (the polar esd is its esd), not the direction.

**A small moment's angles may be freed in the stage that frees its modulus.** They barely move the pattern, and an angle the symmetry fixes not at all. Before 1.9 the default LM driver gave them its largest steps, crawled, and read three tiny steps as `converged`. It now keeps each column's largest scale and measures the curvature of a column it cannot see curve. `solve_magnetic` still frees the moduli a stage first (`SOLVE_STAGE_NAMES`). (Measured: the two-site Pnma set with every moment DOF freed together reaches 3.498/0.700 μ_B at χ²_red 1.0574; its released start had stopped at χ² 454 660; WP-1938, WP-1953.)

## Magnetic-width codes

On `result.diagnostics`, from a fit (WP-1343). The terms are `Phase.magnetic_lor_size`/`_strain`, the magnetic component's own Lorentzian width; the turn-on order is `plan="magnetic_width"` (moment with widths at zero → widths beside the converged moment, which keeps refining → both).

| code | what you must not assume, and what to do |
|---|---|
| `MAGNETIC_WIDTH_UNMODELLED` | (**warning**) Quote the refined moment. `value` is the residual's centre-vs-tails sign split at the magnetic-only reflections minus the same split at the nuclear-only ones, in units of its own noise; a wrong instrument profile or background moves both sets and cancels. Fires only while both widths are held at zero. Run `plan="magnetic_width"` |
| `STAGE_FREES_MAGNETIC_WIDTH_WITH_MOMENT` | (**warning**, from the *plan*, before the first stage runs) Read either number as a measurement of its own quantity. Use the three-step order (`strategy.staged.MAGNETIC_WIDTH_STAGE_PATHS`); silent when the width already has a value |
| `MAGNETIC_WIDTH_UNMEASURED` | (info) Quote a freed width as a magnetic coherence length. `value` = value/esd, against `MOMENT_SUPPORT_SIGMA` (3, the moment's own bar); `None` means back with **no esd**: not measured, never "zero", and the message names the cause it checked (zero magnetic intensity or the zero floor, else none). Expect one of the two terms back this way. Read `MAGNETIC_WIDTH_MOVED_MOMENT` before dropping it |
| `MAGNETIC_WIDTH_MOVED_MOMENT` | (**warning**, from the plan's step-1 and step-3 rungs) Drop a width because it is unmeasured. Quote the released moment and give the width as an upper bound (value + esd) |

## Series codes

On a `SeriesResult` (the series' own `diagnostics`, or a pattern's entry), from a series of patterns whose phase carries a refined moment (WP-1329); a single `fit()` never emits one. The other series codes are in §9b, [series](series.md); the moment trajectory and its onset bracket are described in its *A moment through an ordering transition*.

| code | what you must not assume, and what to do |
|---|---|
| `SEQUENTIAL_MOMENT_HOLD` | Read the held patterns as small moments, or plot them as zero with an error bar. A held point's `value` is its fit's modulus, judged against its *own* esd, so the trajectory withholds the esd there. The message names the successors reseeded to the floor instead of warm-started |
| `SEQUENTIAL_MOMENT_ONSET` | Quote the midpoint as a critical temperature with that ± as its uncertainty: it is a **bracket** between the last released and the first held pattern, the ± half *your pattern spacing*, and nothing fits `m ∝ (1 − T/T_N)^β`. Nor quote it when `MagneticOnset.bracket_verdicts_final` is False (the early-stopped modulus had not finished falling), nor from one pass: `direction="both"` carries both chains' brackets and says whether they overlap, and one chain's warm start can carry a moment across the transition |

## Candidate codes

| code | what you must not assume, and what to do |
|---|---|
| `CHILD_GROUP_UNNAMED` | (info — from `magnetic_supercell`, on the returned statement rather than on a `FitReport`; its `where` is `space_group`, relative to the returned phase) Read the child's `space_group` as a symbol. The group is `phase.symmetry_operations`, and every orbit, multiplicity and systematic absence comes from it; the cell's metric constraints come from the closest type's point group and lattice, which are this group's own. Quote the operation list, or the type **with the cell transform beside it**. Such a group has no Wyckoff letter (`site_constraints(...).wyckoff` is empty) and no `SPACE_GROUP_SETTING_ASSUMED` warning, both being properties of a tabulated setting. A published symbol for the same superstructure names a type in some other cell |

## Interchange codes

A magCIF's atom **positions** refine under the highest tabulated group the file's atoms satisfy — the parent it names where that contains its magnetic operators with time reversal dropped and keeps every listed site's orbit (`CIF_MAGNETIC_NUCLEAR_GROUP` says so, with the index over the file's own group), else the file's own family group (`CIF_MAGNETIC_NUCLEAR_SETTING`) — while the **moments** always refine under the file's magnetic group; read `phases[0].space_group` and those two codes to see which happened. Override with `Structure.from_cif(..., nuclear_group="file")` (always the file's own group) or `nuclear_group="parent"` (always the parent, refused by name where it cannot carry the file's atoms); the default is `"auto"` (issue #457).

**Exporting** a magnetic phase: `Structure.to_cif` writes the magCIF. `rx.write_topas_inp` writes `mag_space_group` (BNS number, no `space_group`) and `mlx mly mlz` as μ_B ÷ edge, each within one ulp on the way back; it refuses by name what a `str` cannot state — a non-standard setting, a nuclear group above the magnetic family group, a moment ion ≠ the site species (both are the one `occ`), either k. `rx.write_fullprof_pcr`, `rx.write_gsas_exp` and `rx.write_gsas2_phase_cif` raise `ValueError` naming the phase rather than write it as a nuclear one — GSAS-II's CIF import drops the magCIF loops (Measured: GSAS-II 5.6.3, issue #470). In `reflection_table` rows of a magnetic phase, `ReflectionRow.f_squared` is the **nuclear** \|F\|² alone while `intensity` carries nuclear + magnetic, so a magnetic-only line (MnF₂'s (1 0 0)) reads `f_squared` 0 beside a large `intensity`; only a `component == "magnetic"` row (magnetic width active) has the magnetic p²⟨\|F_⊥\|²⟩ as its `f_squared` (issue #613).

**A `.pcr`'s `Jbt = ±1` phase** builds only as the moments of the nuclear phase it restates, in that phase's cell with k = 0 and SYMM/MSYM pairs that are axial actions (`FULLPROF_MAGNETIC_PHASE_READ`); every other shape is refused by name, the Fourier-component form included. Its reason is `rietx.io.projects.fullprof.magnetic_reading(model, phase)`, a string, before you build.

| code | what you must not assume, and what to do |
|---|---|
| `CIF_MAGNETIC_ION_UNCHARGED` | (info — from `Structure.from_cif`, pass `diagnostics=[]` to collect it; it is not on `result.diagnostics`) `where` names the site; state it with `Structure.from_cif(..., moment_ions={"Mn1": "Mn3+"})` and the code stops firing. MAGNDATA writes a bare `Mn` for a site that is chemically Mn³⁺, and magCIF has no item for the ion at all. The `suggestion` lists the ions of that element the table does carry |
| `MAGNETIC_ION_ASSUMED` | (info — same reader, same channel) A stronger substitution than the neutral-atom one, so it fires instead of `CIF_MAGNETIC_ION_UNCHARGED`, never alongside it. Every lanthanide and actinide this table carries has only ionic ⟨jₙ⟩ curves (Brown, ITC Vol C), so the default is the element's majority *magnetic* oxidation state (Ln³⁺, except Eu → Eu²⁺ since Eu³⁺ is 4f⁶/J=0; Yb³⁺; U⁴⁺, Np⁴⁺, Pu³⁺; WP-1327 D1). `where` names the site; state it with `moment_ions={"Dy1": "Dy3+"}` and the code stops firing, the same route that silences either one |
| `LANDE_G_ASSUMED` | (info — same reader, same channel; only ever alongside `MAGNETIC_ION_ASSUMED` on the same site) Without this default the site refused one line later, on `resolve_g`, and never loaded at all (WP-1327 D-lande-g). `value` carries the Hund's-rule g_J = 1 + [J(J+1)+S(S+1)-L(L+1)]/[2J(J+1)] (Ashcroft & Mermin, ch. 31) of the assumed ion's ground term. **Never fires for a *stated* ion** (`moment_ions={"Dy1": "Dy3+"}`): there an absent g is the caller's own gap and `resolve_g` still refuses (issue #257 A5). `where` names the site's `.moment.g`; state it with `moment_g={"Dy1": 1.333}` and the code stops firing |
| `CIF_MAGNETIC_SYMMFORM` | (info, or **warning** — same reader, same channel) Assume the file's `_atom_site_moment.symmform` is the constraint the refinement will use. The fit follows the operator list, never `symmform`. At `info` the two agree on the number of free parameters, or `symmform` was unreadable (`value` is `None`). At **`warning`** the file's operator loop and this package's symmetry algebra say different things about one site: check which. `value` is the count `symmform` states, and the message quotes the derived one beside it |
| `CIF_MAGNETIC_MOMENT_ON_ALLOWED` | (info — same reader, same channel) Assume the moment you refine from is the one the file printed. The reader took the nearest point of the allowed subspace within half a unit in the last printed place of every component (m_y = 2·m_x printed 2.045, 4.089). `value` is the largest component move in μ_B. No component moves by more than 0.02 μ_B (`MOMENT_FORM_AGREEMENT_MU_B`), so a bare `0` is never moved by its half-width of 0.5; beyond the print or that cap the phase still refuses the file as incompatible |
| `CIF_MAGNETIC_UNIDENTIFIED` | (info — same reader, same channel) Assume `MagneticSymmetry.uni_number` is populated. It is `None`. The **operator list is the model and is unaffected** |
| `CIF_MAGNETIC_CENTERING_ASSUMED` | (info — same reader, same channel) MAGNDATA always writes the `_space_group_symop_magn_centering.xyz` loop, so this is a hand-written file. If the group has a centring or an anti-centring (`x,y,z+1/2,-1`), add the loop and read the file again; without it the moments refine under a different magnetic group |
| `CIF_MAGNETIC_NUMBER_MISMATCH` | (warning — same reader, same channel) Assume the stored BNS/OG number is the file's. It is the operators' own, and the stated `name_BNS` was dropped. The message names both. Check the loops against the file's source before fitting |
| `CIF_MAGNETIC_PARENT_TAG_UNDEFINED` | (info — same reader, same channel) The parent symbol came from `_parent_space_group.name_H-M`, FullProf's spelling, which `cif_mag.dic` does not define; the phase is the one `_parent_space_group.name_H-M_alt` would have given, so nothing is to be done. Both tags naming different groups is refused (`MagCifError`) quoting both: remove the one that does not describe the structure |
| `CIF_MAGNETIC_NUCLEAR_GROUP` | (info — same reader, same channel; fires on every magCIF read that keeps the parent) Fires on every magCIF read that keeps the parent. The message reads "positions refine under `P 42/m n m`, index 2 over the file's own `P n n m`; moments under the file's magnetic group", and `value` is that index (1 where the parent *is* the file's own group, e.g. a type-III group). At index > 1 the positions carry constraints the file's operators do not impose: right where the parent is the structure's real nuclear symmetry, a choice to check where a distortion accompanies the order. `Structure.from_cif(..., nuclear_group="file")` refines them under the file's own group instead |
| `CIF_MAGNETIC_NUCLEAR_SETTING` | (info — same reader, same channel) Assume `Phase.space_group` is the parent symbol the file names. It is not. The setting is checked against the file's own magnetic operators with time reversal dropped (`crystallography.magcif.nuclear_operations`). Three shapes reach here: a symbol tabulated at another origin or axis choice (measured on Ima2/space group 46, read as `I b m 2`); a symmetry-lowering magnetic group whose asymmetric unit lists one parent orbit as two sites; and `nuclear_group="file"`, which asks for it. Either way the phase carries exactly the atoms the file states. A fourth shape: the file's own group is in a setting **no** tabulated symbol names. The message then reads "carried as its own list of N operations under `P -1 [unnamed in this cell]`": `Phase.symmetry_operations` is the group, the bracketed label only names the closest type, so do not look the label up as a symbol. `Structure.to_cif` carries the list; a symbol-only writer (`.inp`, `.pcr`, `.EXP`) refuses the phase by name. A group whose rotations are in no tabulated orientation (a two-fold along [110]) is refused by name (`MagCifError`): restate the file in a conventional setting |
| `CIF_MAGNETIC_MAGNITUDE_ESD_NOT_STORED` | (info — same reader, same channel) Assume a `Structure` read back from a refinement CIF carries the moment's uncertainty. rietx keeps it in `FitReport.magnetic[i].magnitude_esd`, and `write_refinement_cif` writes it back into `_atom_site_moment.magnitude_su`. `value` is the number the file stated |
| `CIF_MAGNETIC_SPHERICAL_ESD_NOT_STORED` | (info — same reader, same channel) Assume a moment with `stderr=None` on every component was not refined. The message quotes each item whose su was dropped. A crystal-axis row keeps its own su, and a Cartesian row's su is propagated through its linear conversion, so restating the row in either form keeps them |

### The TOPAS and FullProf moment readers

These fire at *import*, from `rietx.io.projects` — the same channel §7g's
`TOPAS_*`/`FULLPROF_*` families use, never on `result.diagnostics` — and are
grouped with the rest of the magnetic family here rather than left in
`references/diagnostics-projects.md` (issue #286), since the question they
answer is the same order-parameter one the rest of this file answers.

| code | what you must not assume, and what to do |
|---|---|
| `FULLPROF_MAGNETIC_PHASE_OMITTED` | (warning — from `rietx.io.projects.fullprof.to_structure(..., nuclear_only=True, diagnostics=[])`) Read the returned `Structure` as the model the `.pcr` describes. You **declared** the omission by passing `nuclear_only=True`, and the message says how large what you dropped is: the phase's index and name, its `Jbt`/`Isy`, its site count, how many propagation vectors it carries, which moment columns are non-zero, and its own `R_Bragg` (also on `value`). Rwp, the remaining phases' scales and every weight fraction absorb the intensity it contributed. Without `nuclear_only=True` a `Jbt = ±1` phase is either read onto its nuclear phase (`FULLPROF_MAGNETIC_PHASE_READ`) or the build **refuses**, naming the phase and why: the Fourier-component form (k ≠ 0, an imaginary part, a magnetic phase), basis functions (`Isy = -2`), a moment matrix that is not ±det(R)·R, no nuclear phase in its cell, or a `Scale × f²` its nuclear phase does not share. The route that always works: a magCIF, which `Structure.from_cif` reads |
| `FULLPROF_MAGNETIC_PHASE_READ` | (info — same channel, without `nuclear_only`) Assume the file's two phases are two in the `Structure`. They are one: the SYMM/MSYM pairs became that phase's `magnetic_symmetry` (BNS in the message, or why it has none) and its moments that phase's sites, in crystal-axis μ_B (`Jbt = -1`'s (M, φ, θ) converted, orthogonal cells only). A site the file freed only in part (say M alone) is read with the whole moment free, and the message names it. Its own Scale, positions and Biso were checked equal to the nuclear phase's and are not kept; refine the one phase. `value` is its R_Bragg |
| `TOPAS_MAGNETIC_GROUP_READ` | (info — from `rietx.io.projects.topas.to_structure(..., diagnostics=[])`) Assume the magnetic group was yours to supply. It was the file's own: `mag_space_group` stated a BNS number (`62.448`, `1.1`) or an OG number, resolved to the operators of its **standard setting**; where those are not a symmetry of the file's `space_group`, cell and sites (a b-unique `14.79` beside `P 1 1 21/b`) the read refuses by name instead (issue #597). Where the `str` stated no `space_group` (TOPAS's own examples and ISODISTORT's export often do not), the message also names the nuclear group the positions refine under: the magnetic operators with time reversal dropped, tier 2 of the magCIF rule above. `where` names `phases.i.magnetic_symmetry` and/or `phases.i.space_group`. If the file's coordinates are in another setting, pass `to_structure(magnetic_symmetry=...)` an operator list; a spec you pass outranks the file's number |
| `TOPAS_MOMENT_CONVENTION` | (info — same channel) Assume `mlx mly mlz` are μ_B. They are not. They are **fractional-basis** components, so the stored crystal-axis moment is (mlx·\|a\|, mly·\|b\|, mlz·\|c\|): a per-axis scale on every cell, never a rotation (TOPAS 6 Technical Reference § 9, p. 65, Fmagc = L·Fmag). The values TOPAS reports on a file's `MM_CrystalAxis_Display` line are the numbers to check the stored components against. (Measured: TOPAS 6's calculated magnetic intensities on a β = 115° cell match this reading pair by pair and in \|m\|, and match neither a crystal-axis nor a Cartesian reading.) |
| `TOPAS_MOMENT_ION_UNCHARGED` | (info — same channel) Write the charge into the site's `occ` (the reader normalises `Cr+3` to `Cr3+`, a form-factor key), or set `Moment.ion` on the built structure. The `.inp` sibling of `CIF_MAGNETIC_ION_UNCHARGED` |
| `TOPAS_MAGNETIC_PART_MERGED` | (info — same channel) Assume the file's two strs are two phases. A `"<name> magnetic part"` `str` whose every site is `mag_only` and carries a moment was merged into `<name>`: its moments, charge states and `mag_space_group` are the merged phase's. Its scale, cell, space group and each site's position, element and occupancy were checked **equal** to `<name>`'s (a file where they differ is refused, as is a part site with no counterpart), so there is one scale to refine. Any other refusal the part states still applies |
| `TOPAS_PHASE_TERM_READ` | (info — same channel) Assume the phase's extinction or magnetic widths are the file's own keywords. A `prm p<i>_extinction`, `p<i>_magnetic_lor_size` or `p<i>_magnetic_lor_strain` was read as that term of phase `i`. If the name is the file's own parameter meaning something else, set the term back on the built Structure |
| `TOPAS_MOMENT_G_HELD` | (warning — same channel) Assume the built model frees what the file's refinement freed. The file refines the site's Landé g (`mg @ …`, or a named `mg`, TOPAS Technical Reference § 9), so g arrives **held** at the file's value and the model has one free parameter fewer per named site. g enters only the ⟨j₂⟩ weight (2/g − 1) of the form factor; set `Atom.moment.g` to try another value |
