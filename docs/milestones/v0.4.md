# v0.4 — differentiable backends: measured acceptance record ✅

**Status: shipped 2026-07-27.** All eight v0.4 work packages (WP-0401…0408)
landed, and the full suite is green: **551 tests, 547 passed / 4 skipped in
8 min 15 s**, of which 39 are `slow` real-data acceptance (`-m "not slow"` is
512 tests in 115 s). Measured 2026-07-27 on an Apple-silicon Mac with
Python 3.12, numpy 2.5.1, scipy 1.18.0, jax 0.11.0 and torch 2.13.0 — every
optional-backend row live. Milestone tracking: [../ROADMAP.md](../ROADMAP.md);
design rationale: [../DESIGN.md](../DESIGN.md).

Delivered in v0.4: the backend op shim the whole hot path now speaks
(0401), the JAX chunked-`jacfwd` backend (0402), the mixed-precision policy
that makes an fp32 residual or solve unspellable (0403), the cross-backend
Jacobian-agreement matrix (0404), true Voigt on a shared Faddeeva `w(z)`
(0405), soft bond/angle/value restraints as penalty rows (0406), the
Bérar-Lelann esd placement fix (0407), and the torch backend with its Apple-MPS
fp32 device row (0408).

This milestone's acceptance criterion differs in kind from v0.2's and v0.3's.
No new physics is being measured against a certificate: v0.4 adds *ways to
compute the same derivative*, so the criterion is (i) cross-backend Jacobian
agreement, (ii) wall-clock reported — never gated — and (iii) **the numpy path
unchanged**. The third leg is the one that would have caught a regression, and
it is checked by the v0.1-v0.3 acceptance suites still passing at their
recorded values.

## Measured acceptance — cross-backend Jacobian agreement

`tests/test_cross_backend.py` (WP-0404), the matrix of every way this package
can produce a Jacobian, each compared per column against the analytic assembly
on the *same compiled state*. Methods: central FD (independent of both the
analytic chain and autodiff), `jax` jacfwd, `torch` fp64 CPU, and each of
numpy/jax/torch under WP-0403's fp32-column policy. Configs: the 18
`ANALYTIC_FAMILIES` on the v0.2 lab state under both peak shapes
(`families`, `families_voigt`), the WP-0401 golden states `toy_lebail`
(+P-spline penalty rows), `toy_pawley` (aux intensity block + overlap
restraints), `toy_rich` (aniso ADPs + March-Dollase + nonzero extinction +
displacement/transparency) and `toy_restraints` (WP-0406's rows), plus the real
`srm660c` and `nac` patterns marked `slow`.

Measured 2026-07-27 with **both** optional backends installed — WP-0404's
published table was taken with no torch — as the worst *live* column
(norm ≥ 1e-6 of the largest column's) over every config, and the column that
owns it:

| method | worst rel-L2, off kink | owning column | worst cosine | on the FCJ kink | multi-histogram |
|---|---|---|---|---|---|
| central FD | 8.81e-4 | `srm660c` `profile.u` | 0.99999987 | 3.03e-3 (`axial_sl`) | 1.76e-6 |
| jax jacfwd | 8.77e-4 | `srm660c` `profile.u` | 0.99999987 | 6.05e-3 (`axial_hl`) | 1.76e-6 |
| torch fp64 CPU | 8.77e-4 | `srm660c` `profile.u` | 0.99999987 | 3.03e-3 (`axial_sl`) | 1.76e-6 |
| numpy + fp32 policy | 3.74e-8 | `toy_pawley` `pawley.I5` | 1.00000000 | 2.55e-8 | 2.66e-8 |
| jax + fp32 policy | 8.77e-4 | `srm660c` `profile.u` | 0.99999987 | 6.05e-3 (`axial_hl`) | 1.76e-6 |
| torch + fp32 policy | 8.77e-4 | `srm660c` `profile.u` | 0.99999987 | 3.03e-3 (`axial_sl`) | 1.76e-6 |

Three things this table says that a pass/fail run does not:

- **Only `srm660c` reaches the 1e-4 decade at all.** Every other config —
  including the Voigt shape and the restraint rows — stays below **3.1e-5** for
  every method (`families` 2.72e-5, `families_voigt` 3.07e-5, `toy_rich`
  1.79e-5, `nac` 2.18e-5, the toys ~1e-6). The worst cell is a property of
  that state's `profile.u` column, not of any backend: FD, jax and torch all
  land there, and the two autodiff backends agree with each other (8.77e-4)
  more closely than either agrees with finite differences (8.81e-4).
- **The fp32 policy over numpy is four orders of magnitude tighter than the
  fp64 backends are** (3.74e-8 vs 8.8e-4) — because it measures only fp32
  representation loss on columns the analytic chain already computed, while the
  autodiff rows measure a genuinely independent derivative. Same bar, different
  quantities. See the next section.
- **The kink is a parameterisation property, and the backends split on it
  predictably.** At axial S/L == H/L the FCJ quadrature split point sits at its
  own non-differentiable zero: torch's `jvp` and central FD take the same
  one-sided branch (3.03e-3 on `axial_sl`) while jax's `sign(0) = 0` subgradient
  goes the other way (6.05e-3 on `axial_hl`). Both are inside the documented
  2e-2 kink bar, which applies only when the state's decoded ratios are equal.

Bars: per-column rel-L2 < 5e-3 and cosine > 0.99999 for the fp64 methods;
2e-2 / 0.999 for the fp32-policy rows (imported from `backend/linalg64.py`, not
restated in the test — that restatement would be the drift the file exists to
catch); 2e-2 / 0.9995 for a column sitting on the documented FCJ S/L == H/L
kink, applied only when the state's decoded ratios are actually equal.

Two structural results behind the table:

- **The stage-boundary recompile is not a source of drift.** Running 3-stage
  plans and comparing the Jacobian across each recompile: `srm660c` Rietveld
  0.0 then 5.9e-6 Frobenius / 6.9e-5 worst column, toy Le Bail 0.0 then 1.9e-7,
  toy Pawley 0.0 then 7.6e-7, against bars 1e-4 / 1e-3. For contrast, letting
  Le Bail *re-extract* intensities at the same boundary moves the same columns
  8.2e-2 (Le Bail) and 3.2e-1 (Pawley) — i.e. the test can tell the difference
  between "frozen state regenerated at the same values" and "the model changed".
- **The Pawley intensity block agrees to round-off**, as an exactly linear block
  must: 6.7e-14 (jax) and 1.1e-10 (central FD, i.e. the step size).

Scope, stated rather than implied: the matrix is (Rietveld × {single, multi}) +
({Le Bail, Pawley} × single). Multi-histogram Le Bail and Pawley **do not
exist** — WP-0308 shipped multi-histogram as Rietveld-only because per-pattern
intensity extractions are not a shared quantity — so those cells are absent, not
skipped.

Central differences, not forward: measured against the analytic column, forward
FD sits 6.2e-3 away on `srm660c`'s `phases.0.cell.a` and 4.7e-3 on `nac`'s — at
or past the 5e-3 bar for reasons that have nothing to do with any backend. The
same columns with central differences land at 4.3e-5 and 2.2e-5. A bar loose
enough for forward FD would be too loose to catch drift.

## Measured acceptance — the fp32-column policy, three ways

The `backend/linalg64.py` boundary (invariant 2: a GPU may compute Jacobian
*columns* in fp32; the residual used for cost and statistics, and the solve,
stay fp64 on host) was validated at three increasing levels of realism:

| level | what it measures | worst column | bar |
|---|---|---|---|
| CPU round-trip (WP-0403) | fp32 *representation* loss crossing the host boundary | 3.7e-8 vs analytic fp64 | 2e-2 |
| **Apple MPS, real device** (WP-0408) | error accumulated *inside* a device fp32 forward | **4.0e-4** vs torch fp64 | 2e-2 |

WP-0403 said in advance not to read its six-orders-of-magnitude margin as
headroom, because a CPU round-trip cannot reproduce error accumulated inside a
device pass. The device measurement bears that out — real MPS fp32 is four
orders of magnitude worse than the simulation — and still sits 50× inside the
bar. The bars were set before the device numbers existed and were not moved
after they arrived.

A reading the matrix above makes available and is worth stating plainly: the
`jax + fp32` and `torch + fp32` rows land on **exactly** their fp64 backends'
numbers (8.77e-4 either way), i.e. against a disagreement that large the fp32
policy contributes nothing measurable. Only the `numpy + fp32` row isolates
fp32 loss, because its reference is the same analytic assembly that produced
its columns. That is why the policy could not be settled on CPU alone.

End-to-end, the part that matters: an **SRM 676a corundum refinement run
entirely on the Apple GPU**, every peak-chain evaluation and every Jacobian
column in fp32, lands **Δa = −3.5e-8 Å, Δc = −4.6e-8 Å, ΔRwp = +5e-11** from
the numpy fp64 refinement (bar 3e-5 Å), with **c/a = 2.7299281** — the v0.3
record's value. For scale, torch *fp64 on CPU* sits further from numpy
(Δa = +3.0e-6 Å) than the fp32 GPU run does: the trust region re-measures every
step against an fp64 cost, so column precision sets the *path*, not the
*answer*. That is the invariant, confirmed on hardware rather than argued.

## Measured acceptance — wall-clock (reported, never gated)

`examples/bench_torch_mps.py`, best of 3, 2026-07-27, on the machine described
above. Two patterns with opposite hot-loop shapes: **11-BM NAC** (22 003 points,
129 reflections × 1 line, no axial asymmetry — 129 windows of 865 points mean,
so per-window overhead dominates) and **SRM 676a corundum** (7 251 points,
64 reflections × 2 lines, 1 383 FCJ nodes with the axial aperture deliberately
opened — 128 windows of 199 points, i.e. more arithmetic per point).

| pattern | quantity | numpy | jax | torch CPU | torch-MPS |
|---|---|---|---|---|---|
| 11-BM NAC | forward | 1.95 ms | 48.3 ms | 5.35 ms | 355 ms |
| 11-BM NAC | full Jacobian (20 cols) | 13.7 ms | 169 ms | 142 ms | 628 ms |
| SRM 676a + FCJ | forward | 5.34 ms | 98.0 ms | 13.4 ms | 601 ms |
| SRM 676a + FCJ | full Jacobian (17 cols) | 23.1 ms | **48.0 ms** | 293 ms | 1 323 ms |

The comparison flatters no autodiff backend and is not meant to: numpy assembles
*analytic* peak-chain columns and never evaluates the forward once per parameter,
while jax and torch run a vmapped `jvp` — the whole forward per seed. Read that
way, the one genuinely informative cell is the bold one: on the
arithmetic-heavy pattern, **jit-compiled jacfwd is within 2.1× of the analytic
assembly** (2.82 ms vs 1.36 ms per column), the case where autodiff's cost model
comes closest to paying for itself. On the window-dominated synchrotron pattern
it is 12× off (8.43 vs 0.69 ms per column). The jit compile itself, measured
per compiled state in the agreement harvest, is **0.8-1.4 s for the toys and
6-11 s for the real configs** — refining WP-0402's "1-4 s per toy stage", and
paid once per stage, not per iteration.

**MPS is a finding, not a speedup:** 112-182× slower than numpy on a forward
evaluation and 46-57× on a full Jacobian. *(This supersedes WP-0408's "60-125×",
which ranged over only part of the same table — the NAC forward ratio is 182×,
not 125×.)* The cause is the loop shape, not the device: the residual walks
~130 frozen windows one at a time in python, so a forward evaluation is a few
thousand kernel launches. MPS per-op cost is **flat at 82-97 µs from 64 to
65 536 elements** — pure launch latency — and the device behaves like a GPU only
at ~10⁶ elements per kernel (265 µs vs numpy's 1 559 µs).

The obvious remedy was then measured instead of assumed. At fixed total work,
batching 128×900 into 1×115 200 takes MPS from 10.2 ms to 0.37 ms (28×) — **and
numpy from 1.31 ms to 0.56 ms**. A size sweep pins the two numbers that settle
it: **break-even ≈ 65 k elements per kernel** (65 536 → 0.97×, 131 072 → 1.67×)
and a **ceiling of ≈2.5-2.7×** (524 288 → 2.46×, 4 194 304 → 2.68×), because
~17 flops per element is memory-bound work in which a GPU's arithmetic
throughput never participates. So:

- the batched peak loop is worth doing as a **numpy-path optimisation**
  (≈2.3×, every user, no optional dependency) — scoped as a measure-then-decide
  spike in [../wp/0605-batched-peak-loop.md](../wp/0605-batched-peak-loop.md),
  not as GPU enablement;
- **device acceleration needs a bigger problem.** Batched, one pattern is
  ~1.1×10⁵ point-evaluations for 11-BM NAC (129 windows × 865 points mean) and
  ~2.5×10⁴ for lab corundum before FCJ nodes — i.e. a lab pattern sits *below*
  break-even even after batching, and a synchrotron one sits just above it at
  ≈1.7×. The ≈2.5× plateau needs several patterns processed together: a
  `vmap`-batched in-situ/parametric series, which is v2-fenced.

`torch.compile` does not rescue it either: 2.5× slower than eager on CPU (13.5
vs 5.4 ms) after a 38 s one-off compile, and on MPS dynamo hits its recompile
limit because `i0, i1 = cp.win[il, k]` specialises on each window's literal
bounds — one graph per reflection. The loop shape defeats compilation for the
same reason it defeats the GPU.

One honest cost recorded against this milestone rather than hidden: the MPS
scalar-wrapper guard (0-d values lifted to device tensors) was called "bounded"
on reasoning and was then **measured at 1.8×**, taking the NAC forward from
199 ms to 359 ms (355 ms in the run tabulated above; torch-CPU unaffected at
~5.4 ms). It was kept — it is what makes the device row correct — but it is
written down as a regression rather than left as an assumption.

## Measured acceptance — the numpy path unchanged

The v0.1-v0.3 acceptance suites are the regression gate for this milestone, and
all **39 `slow` tests pass** in the 2026-07-27 run — 11-BM NAC, SRM 660c,
the GSAS-II fluorapatite tutorial, SRM 676a corundum and the IUCr QPA round
robin, each still inside the band its record states (v0.1-v0.3 milestone
records for the values, `tests/data/README.md` for provenance).

That gate is the weaker of two. v0.4 *did* rewrite the hot path — WP-0401 moved
every operation onto the `xp.*` shim and made the residual pure — so the real
line is `tests/test_backend_shim.py`, which pins **six frozen states**
(`srm660c`, `nac`, `toy_lebail`, `toy_pawley`, `toy_rich`, `toy_restraints`)
**bit-identical** (`np.array_equal`) to captures taken before the refactor.
Here "unchanged" means unchanged, not "within tolerance".

The four skips in the full run are all the same guard —
`test_axial_columns_are_not_silently_fd_routed` on the configs that free no
axial columns — and it skips by design rather than silently passing.

One set of numbers **did** move in v0.4, deliberately, and it is WP-0407's esd
fix rather than a backend effect. The Bérar-Lelann serial-correlation inflation
was being applied to the covariance *before* the correlation matrix was taken
out of it, so every reported physical esd was raw while the docstrings claimed
inflation, and the correlation matrix came back divided by BL² (diagonal
1/BL² = 0.0372 at BL = 5.18; a true ρ = −0.699 reported as −0.026), which left
the 0.98 high-correlation guard **structurally dead**. After the fix:

- SRM 660c `a`-esd = **2.49e-5** (raw 7.4e-6 × BL 3.38). The published headline
  `a = 4.156895(25) Å` was always the inflated number — what changed is that the
  code now agrees with it. A `1.5e-5 < a_err` lower bound was added so a
  regression back to raw fails loudly.
- QPA σ(W) now **0.1-0.9 wt %** (was 0.1-0.4 raw). No QPA tolerance regresses —
  they never leaned on σ(W), which understates systematics-dominated QPA error
  by an order of magnitude anyway.
- Pawley overlapped-pair relative esd ≈ **116 %** (BL ×1.567).
- The correlation matrix has unit diagonal, and the 0.98 guard is live again: it
  fires on collinear zero-shift ~ Bragg-Brentano displacement (ρ ≈ 1.0).

Two unit tests had been riding the bug and were **reconciled to the physics, not
silenced**: co-freeing extinction+scale+Biso is a genuine degeneracy
(ρ(ext,scale) ≈ +0.97), and aniso U11/U33 separate at ≈2.2σ against honest esds
(the assertion was relaxed 3σ → 2σ; the March-Dollase sibling stays identifiable
at worst ρ ≈ 0.28).

## Known gaps — stated, not tuned away

1. **Layer-1 attribution under Voigt is conservative, not exact.**
   `report/layer1.py` reads width slot 1 as an FWHM (line ~90) for its
   0.4·FWHM validity radius; under Voigt that slot is σ ≈ FWHM/2.355, so the
   radius is *tighter* than intended. Safe, slightly suboptimal, unfixed — a
   future WP should expose an FWHM per shape rather than reading the slot.
2. **Restraints are Rietveld- and single-histogram-only.**
   `run_multi_least_squares` raises `NotImplementedError`: the stacked layout
   sizes its below-data slot from the background penalty rows, and a
   per-histogram restraint stripe needs a third offset row-block (deferred into
   WP-0308's `### Inherited`). The bond/angle geometry's four 1-D·1-D products
   are also **untested on MPS** — `toy_restraints` declares value restraints
   only, so that path never reaches the device. Left as a documented gap rather
   than a pre-emptive untested workaround.
3. **fp64 does not exist on any Apple GPU**, and jax-metal is abandoned. jax
   fp64 is therefore CPU-only here, and MPS fp32 is a hardware fact rather than
   a policy choice — which is why the device is selected by a backend *name*
   (`"torch-mps"`) and not by the WP-0403 policy object. Folding it into the
   policy would have made "torch-mps at fp64" spellable.
4. **CUDA is unvalidated on hardware.** The policy is CUDA-ready and
   CPU-tested; `examples/validate_cuda_mixed_precision.py` skips with a printed
   reason on this Mac. It is documentation-as-code for the day a CUDA box
   exists, not a CI gate.
5. **The agreement matrix only covers what its state builders contain.** New
   physics is invisible to it until a config exists — and v0.4 hit this twice
   for real: WP-0405's Voigt shape and WP-0406's restraint rows both shipped
   while no matrix row differentiated them (`toy_restraints` was in `STATES` but
   not in `CONFIG_PARAMS`). Both were wired in when the parallel branches were
   integrated on 2026-07-27, and all 12 new cells passed first time. Still a
   standing hazard for *configs* — **a new derivative path must arrive with a
   config** — though a new *backend* can no longer slip through: see the
   consolidation below.

## Closing the duplication, before the milestone was called done

The engineering note this milestone would otherwise have shipped with — "the
row layout is written out in three places, and the hazard has now been hit once
for real" — described a defect, not a design. It was closed on 2026-07-27,
before the record was signed off, because the next backend or the next row block
would have hit it again and a *test* can only notice afterwards.

What changed, and what each part now guarantees:

- **`model/rows.py` is the row layout.** `BLOCK_ORDER`, `block_sizes`,
  `layout()` and `assemble()` — the numpy residual, the numpy Jacobian's row
  *offsets* (a fourth copy, found during the consolidation: it re-derived
  `n_data + n_bkg_pen + n_res`) and every traced residual now build from it.
  Adding a block is one edit in one file.
- **`backend/traced.py` is the traced twin.** The traceable `decode` and
  residual are written once against `xp` and shared by jax and torch, which
  previously carried near-identical copies. A new backend inherits both.
- **`backend/traced.active(xp)`** binds the backend globally *and* opens its
  precision scope for the duration of a traced call, so a caller cannot
  evaluate traced code in the wrong context — which was previously possible and
  silent.
- **`tests/test_backend_conformance.py` is driven by the registry**
  (`backend.api.BACKEND_NAMES`), not by a hand-written list: op-vocabulary
  parity, transform-op fidelity against `params.transforms.to_physical`, the
  traced decode, and the traced residual against the numpy reference on all six
  golden states — every one inherited automatically by a backend added to the
  registry. Its meta-test fails if a registered backend has no row in
  `test_cross_backend.METHODS`, so a backend cannot ship without its
  agreement bars.

Two real defects surfaced the moment the paths were shared, which is the
argument for having done it:

- **jax constants were being materialised outside the x64 scope.** Lifting them
  at closure-build time made them float32 while everything downstream looked
  fp64; the exactly-linear Pawley aux columns went from 6.7e-14 to 1e-7 against
  the analytic ones. Constants (and θ itself) are now lifted *inside* the traced
  call, where the scope is open — and jax's scope is exposed as
  `Backend.full_precision()` rather than living in one backend's private helper.
- **`to_host_fp64` could not accept a device tensor.** The "single fp64 host
  boundary" raised on an MPS array instead of transferring it, so torch had
  open-coded its own `.detach().cpu()` — a second boundary in all but name. The
  helper now performs the transfer, and is the only place that does.

Measured after the consolidation: the whole suite green, the six golden states
bit-identical, and the fp32 device residual agreeing with the numpy fp64 one to
**3e-5…1.4e-4 rel-L2** — the fp32 forward-pass level WP-0403 predicted from
cancellation at 10⁵ counts, against its 2e-2 bar. A device residual *cannot*
match fp64 and is never asked to; what is asserted exactly for it is the layout.

## Engineering notes

- **Two hot-path rules now bind all future work** (in CLAUDE.md's Conventions):
  never put a frozen numpy constant on the left of a python operator against a
  θ-derived value (`ndarray * tensor` raises on torch; `tensor * ndarray` routes
  through numpy's deprecated `__array_wrap__` and then fails under a functorch
  transform) — route it through `xp.matmul` or lift it with `xp.asarray`, both
  no-ops on numpy; and a *new op* must be added to `_OP_NAMES` and implemented
  on every backend, which `tests/test_backend_torch.py` enforces. Nine hot-path
  sites were lifted this way in 0408, four of them 1-D·1-D dot products in the
  restraint geometry (MPS cannot batch `aten::dot`, which asserts internally
  under a batching rule for every seed-block size except 3).
- **The residual row layout was written out in four places** — the numpy
  residual, the numpy Jacobian's offsets, and the jax and torch traced
  residuals. WP-0406 named the hazard in a forward note; the note was written
  after 0406 shipped, so nobody read it, and 0408 hit it for real when the torch
  residual had to grow the restraint rows. It is now one place
  (`model/rows.py`) — see "Closing the duplication" above.
- **`conj_physical` has no vmap batching rule** in torch — it silently falls
  back to a per-sample python loop over the whole structure factor (15× on
  `toy_rich`).
- **Read the op vocabulary from the code, not from prose.** WP-0401's own
  handover says "~41" in one place and "37 named ops" in another; the shipped
  list is 32 entries in `_OP_NAMES` plus `window_add`/`segment_sum`, plus `pi`
  and `linalg.inv`/`.det`. `src/pxrdref/backend/api.py::_OP_NAMES` is the
  authority.
- Every optional-backend row **self-skips without its package**, so
  `pytest tests/test_cross_backend.py` is green on a numpy-only checkout —
  the agreement CI cannot become an install requirement.
